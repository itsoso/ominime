# Kim/微信发送后最终文本采集设计

## 状态

已确认。目标是只记录用户最终发送出去的完整文本，不保存逐字输入、删除或替换过程。

## 背景与已知问题

当前 Kim/微信正文采集发生在 Enter 发送之前：监听器暂时抑制 Enter，读取 Accessibility 状态，冻结窗口图像，再通过候选词、键盘缓冲或固定输入框 ROI OCR 恢复正文。该链路有三个结构性问题：

- Kim 的 Electron Accessibility 树不暴露输入框文本；微信也不能稳定依赖 AXValue。
- 固定 ROI 会随窗口尺寸、输入框高度和界面版本漂移。实测 Kim 文本可能完整落在当前 ROI 之外。
- 发送前读取与 Enter 竞争。AX、Quartz 或 Vision 变慢时，即使有 watchdog，也会增加吞键、重复发送和工作线程停滞风险。

既然产品只需要最终发送文本，采集时机应从“发送前抢读输入框”改为“发送后确认新增的我方消息”。

## 目标

- Kim 和微信发送普通文本后，在本机异步取得最终消息正文。
- Enter 原始 keyDown/keyUp 直接交给目标应用，不再为了正文采集而抑制或重放。
- 优先使用可信的结构化本地来源；不可用时使用发送后气泡 OCR。
- 只在结果达到明确可信条件时保存正文；失败时记录非内容诊断，不保存猜测文本。
- 图片只存在内存，不落盘、不进数据库、不进入日志、不发送到远程服务。
- 保留现有历史数据库；不恢复 Web 上下文页、上下文 API 或上下文写入。

## 非目标

- 不记录逐键编辑历史。
- 不采集对方消息或聊天上下文。
- 不识别图片、语音、文件或表情包中的内容；这些消息第一阶段只允许明确跳过。
- 不注入 Kim Electron renderer，不 hook 微信进程，不解密应用数据库。
- 不把已经停止维护并提示合规风险的 Chatlog 作为默认或必需依赖。

## 方案比较

### 方案 A：只做发送后 OCR

实现范围最小，两个应用可共用，但 OCR 仍可能出现字符错误；如果没有发送前基线，也可能把旧气泡误判为新消息。

### 方案 B：只读应用本地数据

在接口可用时文本最准确，但 Kim 没有已验证的稳定接口；微信第三方 Chatlog 已停止维护并提示合规风险，直接依赖会引入不可接受的版本、维护和合规风险。

### 方案 C：结构化本地来源优先，发送后 OCR 兜底（采用）

建立统一 `MessageSource` 接口。先尝试 macOS Accessibility 等受支持且只读的结构化来源；没有可信结果时读取新增的我方气泡。来源选择、重试、稳定性和持久化由同一个协调器控制。以后若应用提供官方本地接口，可以新增适配器而不改监听器。

## 总体架构

### 1. SendDetector

EventTap 只完成低成本判断：目标是否为 Kim/微信、是否为普通 Enter、应用是否被忽略、捕获模式是否允许。符合条件时复制必要的标量元数据并把事件放入现有 worker 队列，然后立即返回原始事件。

它不执行 AX、窗口枚举、截图、OCR、HTTP 或数据库操作，也不创建 `PendingReplay`。

### 2. SendIntent

worker 完成安全输入检查后创建不可变发送任务，字段包括：

- `intent_id`
- Enter 的墙钟时间和 monotonic 时间
- 应用名、bundle id、目标 PID
- 按键修饰状态
- 物理按键计数
- 仅用于校验的候选/键盘缓冲摘要
- 最近的内存气泡基线指纹（如存在）

任务不包含聊天上下文或截图路径。

### 3. MessageSourceAdapter

每个来源返回统一结果：`content`、`source`、`message_identity`、`confidence`、`observed_at` 或明确的 `failure_reason`。

来源顺序为：

1. `AccessibilityBubbleSource`：从目标 PID 的 AX 树读取新增的我方静态文本；必须能确定文本属于发送后的新增消息。
2. 未来的官方/受控应用适配器：只有经过单独安全和契约验证后才启用。
3. `VisualBubbleSource`：对当前目标窗口的消息区域执行 macOS Vision 本地 OCR。

本机现有 `127.0.0.1:5030` Chatlog 只视为外部用户环境，不纳入默认读取链路，也不由 OmniMe 自动探测、启动或查询。

### 4. VisualBubbleSource

不再使用固定 composer ROI。它只处理目标窗口的聊天内容区，并使用应用 profile 提供的相对边界作为搜索范围。识别步骤为：

1. 读取发送后的当前窗口帧。
2. 排除顶部导航、左侧会话列表和底部输入工具栏。
3. 将 Vision 行按视觉行、邻近距离和气泡区域聚类。
4. 只保留符合我方方向特征的最下方候选气泡。
5. 与内存基线、任务时间和校验摘要比较，证明它是本次发送后新增的结果。
6. 连续两个采样得到相同规范化文本和稳定几何位置后才返回成功。

为避免第一次采样已经晚于 UI 更新造成的竞态，监听器在用户开始在 Kim/微信输入后通过独立、限频的后台采样器维护最近一张内存基线。采样不进入 EventTap callback，最多保留当前目标窗口的一张图和派生指纹；创建 `SendIntent` 后转移所有权，任务结束立即释放。

### 5. CaptureCoordinator

协调器使用独立有界队列和单 worker，避免 OCR 阻塞键盘事件处理。建议按 Enter 后约 `150ms、350ms、650ms、1000ms、1500ms、2000ms` 采样；结构化来源每轮先尝试，随后才做视觉识别。

成功条件：

- 结构化来源给出唯一消息 ID、我方方向和发送时间范围内的完整文本；或
- OCR 文本连续两次稳定，并同时满足新增证据、我方方向、非边缘裁切、非界面 chrome、长度上限和校验摘要约束。

失败条件包括队列满、窗口消失、应用切换、secure 输入、无法证明新增、OCR 不稳定、超时和本地原生调用异常。所有失败都必须可观测，但不能阻止消息发送。

## 重复发送与并发

- 去重主键优先使用结构化来源的消息 ID。
- OCR 使用 `intent_id + target_pid + observed_at + bubble_geometry + text_hash`，不能仅按文本去重，因此连续发送两条相同文本仍可各保存一次。
- 同一窗口的任务按 Enter 顺序执行；不同 PID 可以排队，但第一阶段保持单 worker，先以确定性换取吞吐。
- 任务队列满时直接记录 `post_send_queue_full`，不阻塞或抑制 Enter。
- 过期任务不能在用户切换会话后继续写入；PID 或前台会话锚点不匹配即失败。Kim 的窗口 ID 不匹配即失败；微信发送会重建原生窗口，只有 PID、窗口尺寸与会话锚点仍一致时才允许沿用发送前逻辑窗口 ID。

## 数据与隐私

- 成功正文继续通过现有 `KeyEvent -> submission_processor -> input_records` 路径保存，不迁移历史表。
- `fallback_source` 使用明确值，如 `kim_postsend_ax`、`kim_postsend_ocr`、`wechat_postsend_ax`、`wechat_postsend_ocr`。
- 失败继续进入 `capture_diagnostics`，只保存来源、阶段、错误码、耗时、重试次数和任务 ID；不保存窗口标题、AX 层级、截图或 OCR 候选文本。
- `submission_contexts` 历史表保持原样且不新增记录。
- 不调用 OpenAI、阿里云或其他远程模型。

## 错误处理

- 所有原生调用在采集 worker 中执行；EventTap callback 永远不等待。
- 每次来源读取有独立超时，整个任务最大约 2 秒。
- OCR/AX 异常必须返回明确失败码，禁止空 `except` 后伪装成功。
- 停止服务时先拒绝新任务，再有界等待当前任务，最后释放内存图像。
- 服务重启后不恢复未完成任务，避免把旧窗口内容误记为新发送。

## 分阶段交付

### 阶段一：发送后基础链路

建立 `SendIntent`、来源协议、协调器和诊断；让 Kim/微信 Enter 直接放行。结构化来源不可用时必须正常进入 OCR。

### 阶段二：动态气泡 OCR

实现内存基线、动态区域、我方气泡判定、稳定双读和相同文本连续发送去重。

### 阶段三：受支持的结构化来源

实现 AX 气泡适配器。任何应用专有来源必须先通过独立 Gate：接口来源受支持、只读、可识别我方方向、具有稳定消息 ID、失败可回退。未通过就保持关闭。

### 阶段四：清理旧链路

删除 Kim/微信发送前冻结、Enter replay/watchdog 和固定 composer ROI 的生产入口；保留通用键盘统计逻辑。

## 验收标准

- Kim、微信的 Enter keyDown/keyUp 均原样只到达应用一次；采集 worker 卡死也不影响发送。
- 短中文、英文、数字、标点、表情字符、多行、粘贴、Doubao 候选和连续相同文本均能按最终消息保存。
- 快速连续发送 100 条时无重复、无串话、无无限队列增长，Python 进程和 EventTap 持续存活。
- 改变窗口大小、输入框高度、切换会话和收发消息交错时，不能保存旧气泡或对方消息。
- secure、ignored、count-only 和非普通 Enter 不截图、不 OCR、不保存正文。
- 所有图片只存在内存；数据库、日志、诊断和 Web API 均无截图或上下文内容。
- Web 统计只纳入已确认正文；失败只影响失败计数。

## 已实现的信任边界

实现采用发送前内存窗口帧与发送后当前帧的不可逆标题区域感知指纹，同时校验 PID、逻辑窗口身份和前台应用。Kim 的原生窗口 ID 必须严格一致；微信发送若重建原生窗口，只有 PID、窗口尺寸和会话指纹均保持一致时才沿用发送前逻辑窗口 ID。该指纹容忍激活态亮度与少量抗锯齿漂移，但不同真实会话必须超过严格汉明距离阈值并失败关闭。Visual 来源只有在本地 validation 摘要存在且与完整候选精确一致时才允许成功；空摘要即使只有一个右侧 OCR 行也会失败，避免滚动产生的粗变化区域把旧消息误判为新增消息。Latin/数字来自本地按键缓冲，Shift/Option+Enter 保留换行；粘贴在 Cmd-V keyUp 后由事件 worker 优先读取一次当前 composer AX 值，AX 不可用时只记录不含正文的 pasteboard changeCount。Enter 通过 secure 检查、确认剪贴板未变化且没有前后混合输入后才瞬时读取字符串作为 validation；其余情况一律失败关闭。

基线采样、AX 与 Vision 均不在 EventTap callback 内执行。Enter worker 最多有界等待正在生成的基线，EventTap 始终直接返回原事件。图片只在 `WindowFrame` 与来源调用栈中短暂持有，发布或任务结束时显式转移/释放；诊断只包含命名失败码和非内容标识。

默认来源链严格为本地 AX 后本地 Vision。实现没有远程模型调用，没有 Chatlog/5030 探测，也没有微信数据库读取。CPython 无法强制终止任意卡死的原生线程，因此进程级全局槽最多容纳一个失联来源 worker；后续读取在该调用返回前 fail-closed。受支持的来源实现 cooperative cancel，超时后可释放底层图片并恢复同一协调器。
