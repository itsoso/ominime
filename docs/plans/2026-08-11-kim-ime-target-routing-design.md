# Kim 输入法事件归属修复设计

## 背景

Kim（Bundle ID `Kem`）的输入框无法稳定通过 Accessibility 读取正文，因此 OminiMe 会记录物理键数量，并在 Enter 按下前冻结 Kim 窗口，随后用本地 OCR 恢复可见正文。OCR 结果必须与物理键数量合理匹配，避免把窗口水印或其他界面文字误存为正文。

2026-08-11 的现场记录显示，Kim 的连续 Enter 提交全部以 `physical_key_count=0` 和 `no_trusted_content` 被跳过。用户确认正文是键盘直接输入。代码追踪发现，EventTap 回调已经取得已验证的前台应用 Kim，但工作线程随后无条件使用原始事件的 target PID 重新解析应用。中文输入法处理普通字符时，原始事件可能指向输入法进程；最终 Enter 仍指向 Kim。结果是字符没有进入 Kim 的计数和候选状态，而 Enter 在 Kim 路径中看到零计数。

## 目标

- 中文输入法承接字符事件时，仍将字符归属到已验证的前台 Kim 或微信进程。
- 保留原始事件 PID，避免破坏普通应用的精确事件目标解析。
- 保留现有应用切换和预提交画面身份校验，不能把其他应用的输入串入 Kim。
- 不放宽零计数 OCR 信任规则，继续阻止水印和界面文字误存。
- 最终跳过提交时保留候选读取和预提交画面的失败诊断。

## 方案比较

### 方案 A：同时携带原始事件 PID 与已验证前台 PID（采用）

EventTap 回调把原始 target PID 和缓存的前台应用 PID 一并写入 `RawKeyboardEvent`。工作线程仅在前台 PID 与回调采样的应用身份一致、且该应用属于受支持的 Kim/微信目标时，使用前台 PID 作为正文捕获目标；其他应用仍沿用原始 target PID 解析。

优点是能覆盖输入法进程代收字符的真实路径，同时保留应用切换防护和普通应用现有行为。代价是事件结构增加一个明确字段。

### 方案 B：完全信任回调里的应用名称和 Bundle ID

实现最少，但前台应用切换的瞬间可能沿用过期缓存，重新引入错误归属风险。

### 方案 C：允许零物理键计数的 OCR 正文

能掩盖当前丢失，但会移除 OCR 与真实输入行为之间的关键交叉校验，Kim 水印或其他界面文字可能被保存。安全边界不可接受。

## 数据流

1. EventTap 回调读取原始事件 target PID，同时读取已由应用观察器缓存的前台 `(app_name, bundle_id, pid)`。
2. 回调继续按现有严格条件冻结 Enter 前画面：Enter 必须无修饰键、非重复，并且原始 target PID、前台 PID和已预备身份一致。
3. `RawKeyboardEvent` 同时携带原始 target PID 和前台 PID。
4. 工作线程选择正文捕获目标：
   - 对已验证的 Kim/微信，使用前台 PID 和回调采样的应用身份记录字符、读取候选、准备窗口和捕获 Enter 上下文；
   - 对其他应用，继续通过原始 target PID 解析应用。
5. Enter 处理继续优先使用 AX、已确认候选和键盘正文，最后才使用本地 OCR；OCR 的物理键匹配规则不变。
6. 如果所有来源失败，`no_trusted_content` 诊断包含已有的候选失败和 `kim_ocr_failure` / `wechat_ocr_failure`。

## 测试与验收

- 回归测试构造“字符原始 PID 属于输入法、前台 PID 属于 Kim；Enter 原始 PID 属于 Kim”的序列，断言字符计数进入 Kim，可信 OCR 正文被保存。
- 断言普通应用仍按原始 target PID 解析。
- 断言前台身份未验证或应用切换不一致时，不信任前台 PID。
- 断言零物理键计数仍不能直接放行 OCR。
- 断言最终 `no_trusted_content` 记录保留预提交画面失败原因。
- 定向测试通过后运行完整测试；重启 `com.ominime.app`，检查进程、健康接口和新诊断。
