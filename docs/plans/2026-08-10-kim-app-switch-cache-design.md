# Kim 跨应用切换缓存设计

## 背景

Kim 主应用是 `/Applications/Kim.app`，Bundle ID 为 `Kem`。本机还存在显示名为 Kima、Bundle ID 为 `Kim` 的另一应用；它不在本功能范围内。

当前监听器在前台应用切到 ChatGPT、Chrome 等不支持本地输入区识别的应用时，会清空整张已验证 PID 身份表。用户随后切回 Kim 并把 Enter 作为第一键时，Enter 回调可能早于 Kim 窗口重新预备完成，导致已能在发送前识别的正文仍被跳过。

## 方案

- 已验证身份按 PID 保留，不因其他应用激活而整表清空。
- 激活 `Kem` 时只更新 Kim 主进程 PID；预备失败只删除该 PID。
- 激活微信时同样只更新微信自己的 PID，避免两条支持路径互相清除。
- Kima 的 Bundle ID `Kim` 不在捕获映射中，不会被预备或使用本地画面。
- Enter 回调继续要求前台应用名与 Bundle ID、前台 PID、事件目标 PID以及已验证身份完全一致；保留缓存不会放宽授权条件。

## 隐私与性能

跨应用保留的是 PID 与应用身份，不包含正文或图片。窗口预备只枚举窗口元数据；画面仍只在无修饰键 Enter 且普通正文来源失败时冻结，OCR 仍在工作线程执行。

## Kim 水印边界

真实验收中，Kim 的斜体平铺水印可能贴近 ROI 左右边缘。正文组装已经排除这类水印，但旧边界检查发生在过滤之前，导致安全范围内的短句被误报为 `kim_ocr_edge_clipped`。边界检查应复用同一份正文候选过滤结果：只忽略已满足重复、倾斜和分布特征的水印，真实正文仍执行原有四边阈值。

## 测试与验收

- 回归测试复现 `Kem` 已预备 → 激活 ChatGPT → 切回 Kim 第一键 Enter，断言 Kim 画面仍被冻结。
- 测试明确断言 Bundle ID `Kim`（Kima）不会建立预提交捕获身份。
- 回归测试使用真实 Kim 水印坐标，断言贴边水印不会触发正文裁剪，但正文贴边仍会拒绝。
- 现有前台 PID 不一致、身份不一致、微信冷启动与 EventTap 无枚举测试保持通过。
- 部署后在正确 Kim 主进程中发送唯一短句，数据库正文完全一致且来源为 `kim_presubmit_ocr`；随后继续微信验收。
